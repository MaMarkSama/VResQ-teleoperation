# V-ResQ Quest Link Operator 2026.11.16.2

## Quest controller mapping and drive safety

Controls contains editable A, X, Y and right-stick-click bindings, speed limit,
deadzone, steering gain, drive/steering inversion, servo pan and profile saving.
Defaults are A for headset view, X for next robot camera, Y for Controls,
right-stick click for servo center. Left stick drives forward/reverse and turns.
Right stick pans the robot servo. It does not rotate the tracked headset rig.
Left-stick click arms/disarms. B always requests E-stop. Left Menu opens/closes
Controls when the runtime delivers that button to the application.

Driving starts disarmed. Choose Arm and return Live, release the stick to neutral,
then hold left grip while driving. The grip requirement can be changed explicitly
in Controls. Speed and gain settings are bounded. Opening a menu, losing focus,
losing Quest tracking, losing fresh authorized telemetry, or changing the selected
robot disarms control. Reconnection requires re-arming. Keep robot E-stop available.

Headset-only test hides the HUD after enabling passthrough and disarming the robot.
Press Y with the default mapping, or the left Menu button, to restore the HUD.
B also restores the HUD while requesting E-stop. Arming is blocked during this test.
Test while stationary. System export now includes composition layers and blending.

The footer shows commands actually sent through the WebSocket and the ESP32
command RX counter reported by telemetry. Missing counters show unreported.
These are distinct observations. A successful WebSocket send is not an ESP32
acknowledgement. The updated jetson/app.py replies with an opt-in command_ack for
drive sequences and actions. This ACK confirms Jetson acceptance only. It does not
confirm ESP32 execution or physical wheel motion. Legacy backends remain compatible
and display no Jetson ACK. Deploy the updated backend and restart the Jetson service
to enable ACKs. No ESP32 firmware change is required for this interface update.

Motion actions require armed, fresh, authorized control. The back-out action uses
the backend's backout command. Return home uses the backend's existing timed-drive
path replay. It is not localization-based AMR navigation. Use supervised testing
with clear space and an available emergency stop.

## Web monitor parity

Protocol uses /api/system, matching the web monitor's serial, dashboard and camera
schema. Its overview groups protocol contract, link health, integrity, latency,
robot state, command path, faults and camera diagnostics. Raw JSON remains available.
Swarm loads /api/swarm, /api/swarm/map and /api/swarm/timeline, displays node health,
roles, versions, server-reported poses and events. The node selector connects to
an explicitly selected advertised IP/port. Rescan LAN requests the existing local
discovery loop to rescan, which can take several seconds.

Swarm positions are rendered as unvalidated server poses without measured-distance
claims. They may come from simulation or timed motor estimates. No navigation or
formation command is generated by clicking the map. Group mission dispatch remains
read-only in this Unity view. This update is not a new autonomous navigation stack.

## Install on the headset PC

Extract the complete ZIP. Keep VResQ-Operator.exe, its Data folder, UnityPlayer.dll
and the other included files together. Enter Quest Link or Air Link, then launch
VResQ-Operator.exe. The robot and the headset PC must be reachable over the LAN.
This package is a Windows Link player, not an Android standalone APK.

## Operator pages

- Live retains robot video, fleet selection and controls.
- Telemetry reads all fields from the selected robot's /api/state response.
- Protocol reads /api/protocol with TX/RX, CRC counters and telemetry age.
- Swarm reads /api/swarm from the selected robot. Monitoring is read-only.
- System combines /api/system with local operator XR diagnostics.

Payload pages support scrolling, Page up, Page down, Refresh and Save payload.
Unknown nested JSON fields are retained. Missing summary fields display --.
Unavailable endpoints display the HTTP/network error and retry. Old data remains
marked stale. Source changes clear the previous robot's payload.
Robot firmware must expose the corresponding APIs for those pages to populate.

## Headset camera diagnosis

Developer runtime features and Pass-through over Meta Horizon Link were reported
enabled on the headset PC. Their state alone does not confirm successful runtime
passthrough composition. Physical passthrough still needs verification there.

On that PC, open System and choose Save payload. The JSON includes the actual
XR loader, runtime version, XR_FB_passthrough extension, AR session state,
camera subsystem state, OpenXR feature flags, camera alpha and Player.log path.
Local XR diagnostics remain available when the robot API is unreachable.
Send that JSON and Player.log when the headset camera remains black.
Restart XR is an explicit recovery action that restarts the local XR session.
It temporarily interrupts headset tracking. Use while stationary.

The Headset view toggle controls headset passthrough. Robot monitor controls
robot video independently. A running camera subsystem is diagnostic evidence,
not proof that physical passthrough pixels are visible in the headset.

## Validation

AutoBuild_Unity.bat repairs component wiring, runs regression and UI raycast
checks, then builds the Windows player. Test captures under Logs use clearly
marked fixtures. They do not represent connected robot telemetry.
The tests do not invoke drive commands. They cover mouse-pointer UI hit targets
and XR rig wiring. Physical controller/hand presses and passthrough require
testing on the headset PC.

The new attitude instrument smooths valid pitch/roll and displays unavailable
when telemetry is missing, stale or invalid. It does not fabricate IMU readings.
Serial turnaround diagnostics are not presented as measured end-to-end RTT.
